## P2 · 项目背景与痛点

**【布局】** 左右对比：左"传统方式痛点"，右"HAJIMI 一步到位"，中间箭头。

**【正文要点】**
- 痛点：软件操作门槛高 —— 找不到按钮、看不清入口、教程与界面对不上
- 受众：新手用户、老年用户、视障用户
- 传统方案：查教程 / 按 F1 / 反复切窗口，费时且易错
- 我们的答案：一句话，系统直接定位并代为操作

**【图片】** `[IMG-P02]` 左右对比示意图 — 见 `images/P02_pain_vs_hajimi.png`（自动生成）。

**【讲稿】** 普通用户面对复杂软件常常"知道要做什么，却找不到在哪点"。老年和视障用户更明显。传统办法是查教程、切窗口，效率低。我们希望把这条链路压缩成一句话：用户说目标，系统看屏幕、想步骤、动手做。

## P4 · 技术架构（四层）

**【布局】** 自上而下四层堆叠图：表示层 / 应用层 / 服务层 / 数据层。

**【正文要点】**
- **表示层**：PyQt5 桌面面板 + 透明覆盖层 + Web 管理面板（Vue3）

- 三进程：**B 端 PyQt5 → A 端 FastAPI:8010 → OmniParser/LLM**

**【讲稿】** 架构分四层。最上是表示层，包含桌面端两个窗口和 Web 管理端；应用层负责真正"动手"和状态管理；服务层是 A 端 FastAPI，对外 26 个接口，内部做 LLM 规划、风险评分和红线检测；数据层是 SQLite 七张表，加上远程 GPU 上的 OmniParser 和云端大模型。运行时是 B、A、AI 三进程协作。

## P5 · 核心业务流程（时序）

**【布局】** 竖向时序图：用户 → B 端 → A 端 → OmniParser → 执行引擎。

**【正文要点】**
- ① 用户语音/文本下达目标
- ② B 端 mss 全屏截图 → POST `/execute`
- ③ A 端 → OmniParser 解析元素 + SoM 标注
- ④ A 端 风险评分 + 红线检测 + LLM 规划步骤
- ⑤ SSE `/stream/{task_id}` 实时推送
- ⑥ B 端 pyautogui 执行 → `/audit/report` 回传

**【图片】** `[IMG-P05]` 核心业务时序图 — 见 `images/P05_sequence.png`（自动生成，源自 UML 图2）。

**【讲稿】** 一条完整链路是这样：用户说话，B 端截图后把指令和截图发给 A 端；A 端先让 OmniParser 认出屏幕元素，再做安全检查，然后用大模型规划出带坐标的步骤；步骤通过 SSE 流式推回 B 端，由执行引擎逐步操作；每一步结果都会审计上报，供管理端分析。
